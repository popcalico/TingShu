# 技术决策记录（ADR）

> 只记录**会让人产生"为什么不那样做"疑问**的决策。每条包含：背景 / 备选方案 / 决定 / 理由 / 代价。
> 想推翻其中任何一条之前，请先读完理由，并确认你的方案能同时解决"代价"那一栏的问题。

---

## ADR-001 保留 Flutter，不用原生 Kotlin 重写

**背景**：用户要求"创建一个安卓工程"并"基于 abts 改造"。但 abts 是 Flutter 工程（60 个 dart 文件，约 16000 行），不是原生 Android。

**备选**：
1. 原生 Kotlin + Jetpack Compose 重写
2. 保留 Flutter，改造 UI 与业务

**决定**：方案 2。

**理由**：
- 原项目最贵的资产是 `bili_client.dart` + `wbi_signer.dart` + `cookie_jar.dart`：B 站的 WBI 签名、buvid 激活、`-412/-352` 风控退避。这套东西是长期逆向的产物，重写等于重做一次逆向，且 B 站一改就失效。
- Flutter 产出的是标准 APK，对"安卓 App"这个交付形态没有影响。
- UI 重做在 Flutter 里成本更低（热重载 + 声明式布局）。

**代价**：
- 需要安装约 1.8GB 的 Flutter SDK（本机原本没有）。
- APK 体积比原生大（当前含 libmpv 约 40MB+）。
- 老机型（1GB RAM）可能有轻微掉帧，已通过"进度按秒节流 + 关闭水波纹"缓解。

## ADR-002 音频"先落盘再播放"，不做边下边播

**背景**：夸克直链与 B 站音频地址**都要求带特定请求头**（夸克要 `Cookie`+`Referer`+`UA`，B 站要 `Referer`+`UA`），直接交给播放器会 403。

**备选**：
1. 播放器直接读远端 URL（附带请求头）
2. 先下载完整文件到本地，再播本地文件
3. 本地起 HTTP 代理，边下边播 + Range 支持

**决定**：方案 2（v1）。

**理由**：
- 方案 1 对 media_kit 可行（支持 `httpHeaders`），但一旦网络抖动/地址过期（夸克直链约 1 小时失效）就会中断，且无法同时完成缓存。
- 方案 3 最完美，但要实现"稀疏文件 + 多 Range 连接 + 按可用区间阻塞读"，约 500 行，且要处理 seek 到未下载区间的复杂逻辑。
- 方案 2 换来的是**播放器只读本地文件**——稳定、可离线、缓存顺手做完，代码量最小。
- 关键可行性支撑：评书 mp3 通常 10~20MB，配合**预取后两回**，只有"第一次打开某一回"需要等十几秒。

**代价**：
- 首次打开某一回有等待（UI 上给了进度圈 + "正在准备这一回…"文案）。
- 存储占用（由 10G LRU 兜底）。
- 若将来要消除这个等待，按方案 3 演进，`CacheEngine.obtain()` 是唯一需要替换的入口。

## ADR-003 新建 `TingBook/TingChapter` 模型，不复用原 `Book/Chapter`

**背景**：原模型强绑 B 站字段（`bvid`/`aid`/`cid`/`mid`/`pages`），而夸克的书是"文件夹 fid + 音频文件 fid"，字段完全不同。

**备选**：
1. 扩展现有 `Book`，加可空字段
2. 新建统一模型 + `source` 枚举

**决定**：方案 2。

**理由**：
- 加可空字段会让 `Book` 变成"两种东西的并集"，所有读取点都要判空，`ShelfStore` 的序列化也会被污染。
- 统一模型只有 4 个字段真正必需：`id`、`source`、`title`、`chapters`；`chapters[].key` 在 B 站是 cid、在夸克是 fid，用同一个抽象位置存放，播放层不需要知道来源差异。

**代价**：搜索结果需要一层转换（`BiliSource.search()` 里做），但只在一处。

## ADR-004 夸克登录用原生 WebView + MethodChannel，不用 WebView 插件

**背景**：需要读取用户登录夸克后的 Cookie。夸克的关键凭证 `__puus` / `__pus` 是 **HttpOnly**，网页 JS（`document.cookie`）读不到。

**备选**：
1. `flutter_inappwebview`（有 `CookieManager.getCookies`）
2. `webview_flutter`（官方，但公开 API 不支持读 HttpOnly Cookie）
3. 原生 `WebView` + `CookieManager.getCookie()` + MethodChannel

**决定**：方案 3。

**理由**：
- 方案 1 实测**与 AGP 9 不兼容**：`flutter_inappwebview_android-1.1.3` 的 `build.gradle` 用了 AGP 9 已删除的 `getDefaultProguardFile('proguard-android.txt')`，配置阶段直接失败。而项目必须用 AGP 9（见 ADR-006）。
- 方案 2 读不到 HttpOnly Cookie，直接不可行。
- 方案 3 完全可控，约 120 行 Kotlin，还能顺带做原生 UI（登录页样式与 App 一致），并去掉一个体积不小的第三方插件。

**代价**：
- 登录页是原生 Activity，不是 Flutter 页面（视觉上略有不一致，但属一次性操作，可接受）。
- 需要在 `MainActivity` 维护一个 `MethodChannel("tingshu/quark_login")`。

## ADR-005 缓存淘汰："已听完优先"，而不是"播完立即删"

**背景**：用户原话"播放完之后自动删除"，但在澄清环节选择了"**超 10G 才删最旧的**"。

**备选**：
1. 每回播完立刻删文件
2. 严格 LRU（最久未听优先删）
3. **已听完优先删 + 其次 LRU**

**决定**：方案 3。

**理由**：
- 方案 1 与"老人回头重听"直接冲突：网盘限速下重听要再等十几秒。
- 方案 2 可能删掉"刚听完但想再听一遍"的那一回，体验上很刺眼。
- 方案 3 同时满足两个诉求：空间告急时先清已听完的（用户已经消费过），保留未听完的与最近听过的。

**实现**：`CacheEntry.finished` 标记，`evictIfNeeded()` 排序时 `finished` 优先，然后按 `lastUsedAt`。达到上限后一次性回收到 85%，避免每回都触发淘汰。

**代价**：与用户最初的"播完即删"字面表述不同，已在交付说明里解释清楚。

## ADR-006 升级到 AGP 9.3.1 + Gradle 9.5.0，而不是把 Flutter 降版本

**背景**：原项目用 AGP 8.11.1 + Gradle 8.14，Flutter 3.50 拒绝构建。

**备选**：
1. 升级 AGP/Gradle 到官方模板组合
2. 降级 Flutter 到与 AGP 8 匹配的版本（如 3.24）
3. 用 `--android-skip-build-dependency-validation` 强行跳过检查

**决定**：方案 1。

**理由**：
- 方案 3 实测**行不通**：跳过校验后仍然报 `ApplicationExtension.getDefaultConfig()` 不存在——Flutter 插件的字节码是按 AGP 9 API 编译的，这是真实的 API 差异，不是版本号检查。
- 方案 2 会把 Flutter 降到 2024 年的版本，丢掉对新 Android 版本、新 Dart 特性的支持，且以后每次升级都要再痛一次。
- 方案 1 的代价是必须适配 AGP 9 的 DSL 变更和插件兼容性，但这是**一次性**成本。

**代价（实际付出的）**：
- `app/build.gradle.kts` 必须重写（`kotlinOptions` → `kotlin.compilerOptions`）。
- 必须先装 NDK 28.2.13676358（2.1GB）。
- 必须移除不兼容 AGP 9 的插件（`flutter_inappwebview`）。

## ADR-007 字号写死在主题里，并钳制系统字体缩放

**背景**：适老化最直接的做法是"跟随系统字体放大"，但老人常把系统字号开到最大（2 倍），会导致布局溢出、按钮文字被截断。

**决定**：主题里写死一套适老化字号（正文 21sp、标题 26sp、大标题 34sp），同时把系统缩放钳制到 `1.0 ~ 1.25`。

**理由**：
- 我们的基准字号本身已经是系统默认的 1.4~1.6 倍，再叠加系统 2 倍会失控。
- 钳制后仍尊重"用户想让字更大"的意愿（1~1.25 倍区间），但不会破坏布局。

**代码位置**：`main.dart` 的 `MaterialApp.builder` 里对 `MediaQuery.textScaler` 做 clamp。

## ADR-008 首页只保留三个可点区域

**背景**：适老化不是"放大"，而是"减少选择"。

**决定**：首页只有——① "继续收听"大卡片 ② 书架网格里的书 ③ 底部"全部书架/设置"两个键。没有搜索框、没有分类、没有推荐流。

**理由**：
- 老人打开 App 的唯一意图是"接着上次听"，所以"继续收听"必须是最显眼、最大的目标（卡片内按钮高 72dp，字号 26）。
- 搜索/添加属于**家属**操作，收进"全部书架 → 添加评书"，常人路径里不出现。
- 设置页是家属配置用，但入口必须存在（老人可能需要在别人电话指导下点开），所以放在首页底部而不是隐藏手势里。

**代价**：老人无法自己找新书。这是刻意的取舍——找书由家属负责。

## ADR-009 先出声再存盘（边听边存），不做"下载完才播"

**背景**：最初为了绕开 B 站/夸克直链需要 Cookie/Referer 的问题，采用"整回下载到本地再播"。
单回 30~100MB 时，点开要转圈几十秒；老人不会等，会以为软件坏了直接退出。

**决定**：没缓存时用 `_mp.open(Media(url, httpHeaders: ...))` **立刻流播**，
同时后台把整回补齐到本地缓存；有缓存时仍走本地文件。

**理由**：
- 老人对"多久出声"的容忍度极低，第一秒有没有声音决定他会不会继续用。
- media_kit（mpv）原生支持 http 流 + 自定义请求头，能直接带上 Referer/Cookie，
  不需要再为"直链 403"付出等待成本。
- 本地缓存的价值（断网可听、下次秒开）由后台任务补上，两条路互不阻塞。

**代价与对策**：
- **双倍流量**：播放器拉流 + 后台下载同一文件。对评书（单回几十 MB）可接受；
  后台任务与预取队列共用串行队列，不会无限并发。
- **直链可能流不动**：`_watchStreamFallback` 8 秒没读出时长就退回下载模式，
  且 `await` 的是后台同一个下载任务，不会重复下载。
- **进度不确定**：流播时进度条没有百分比，文案改成"边听边存，不用等整回下完"。

**代码位置**：`lib/player/ting_player.dart` 的 `_playCurrent()` / `_watchStreamFallback()`，
`lib/services/cache/cache_engine.dart` 的 `saveInBackground()`。

## ADR-010 通知折叠视图的按钮索引必须现算

**背景**：`PlaybackState.androidCompactActionIndices` 曾写死 `[0, 2, 4]`。
`controls` 是动态的（第一回没有"上一回"、最后一回没有"下一回"），
4 个元素时索引 4 越界。Android 12 及以下构建媒体通知会抛
`IndexOutOfBoundsException`，**整个进程闪退**；Android 13+ 不调这段 API，不崩但行为异常。
Dart 侧只有 `assert(length <= 3)`，不校验索引范围，release 下会原样传给原生。

**决定**：索引一律由 `controls` 现算并过滤越界值，抽成顶层函数
`compactActionIndices()`，用 `test/media_controls_test.dart` 穷举 8 种状态组合锁死。

**理由**：这类"只在特定机型/特定回目才炸"的 bug，靠手工点很难覆盖；
纯函数 + 穷举测试是唯一能长期防回归的方式。

**顺带约束**：`_pushState()` 必须节流（≥800ms），否则进度流会让通知每秒重建十几次。
