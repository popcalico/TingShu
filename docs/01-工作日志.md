## 0. 任务与需求解读

### 0.1 原始需求（用户原话要点）

1. 以开源项目 `github.com/fengqiao57/abts` 为基础，改造出一款安卓 App，名称为**听评书**。
2. 做**高度适老化**改造，UI 越简单越好。
3. **只保留评书**内容。
4. 保留原工程中评书内容的拉取能力。
5. 新增功能：获取**夸克网盘**里存储的评书内容；播放源选夸克时**自动缓存 10G**，随听随缓，**播放完自动删除**。
6. 要求先分析可行性、列计划、有疑问就提问。

### 0.2 需求拆解与隐含约束

| 需求 | 隐含约束 | 处理方式 |
|---|---|---|
| 保留原工程评书拉取 | 原工程是 Flutter，取流链路包含 WBI 签名 + buvid 风控，重写成本极高 | 保留 Flutter，复用网络层 |
| 只保留评书 | 需要砍掉广播剧/相声/有声小说/UP主/合集/登录/主题/TV 等模块 | 60 个 dart 文件砍到 15 个 |
| 高度适老化 | 不能只是放大字体，要减少层级和选择 | 首页只留"继续收听"+书架，播放页只有 4 个键 |
| 夸克网盘 10G 缓存 | 夸克无面向 App 的开放 API，且直链需带 Referer/Cookie | 换直链 + 先落盘再播 + LRU 淘汰 |
| "播放完自动删除" | 与"重听不想重新下载"冲突 | 用户选择"超 10G 才删最旧的"，实现为"已听完优先删" |

### 【17:03】网络实测

**目的**：确认两条内容链路在本机网络下真的通。

**动作与结果**：
```bash
curl https://api.bilibili.com/x/web-interface/nav              → 200 ✅
curl "https://api.bilibili.com/x/web-interface/search/type?..." → 返回 HTML ⚠️
curl https://drive-pc.quark.cn/1/clouddrive/config             → 401 ✅（缺 Cookie，接口存在）
```

**分析**：
- B 站搜索接口裸请求返回 HTML 是**风控页**（缺 WBI 签名与 buvid）。原工程的 `BiliClient` 正是为解决这个而存在，说明**不能自己裸写请求**，必须复用它的签名链路。
- 夸克返回 401 而非 404/连接失败 → 接口路径正确，只是没鉴权。**可行性成立**。

### 【17:04】夸克网盘可行性取证

**目的**：判断"App 读取用户网盘评书"到底能不能做、风险在哪。

**动作**：两次 WebSearch + 拉 OpenList 驱动源码。

**结果**：
1. **夸克没有面向第三方 App 的开放 API**。官网提到的"支持 AI Agent 调用"是给 PC 端 Agent 的 Skill（OAuth + 云端网关），塞不进普通安卓 App。
2. 社区实践（OpenList / quark-nd-mcp）统一走网页版逆向接口 + Cookie。
3. **限速数据**（多来源交叉）：
   - 免费用户 300KB/s ~ 1MB/s
   - SVIP 20~50MB/s
4. **官方文档明确警告**：夸克限速导致 OpenList 只能走本地代理传输。

**关键推算（决定了方案可行性）**：
> 评书 mp3 普遍 32~64kbps → 30 分钟约 **7~14MB**。
> 即使按最差的 300KB/s，一路 30 分钟的内容也只需 **25~45 秒**下完。
> → **限速对音频流播影响很小**，这是整个方案能成立的核心前提。

**结论**：可行，但有三个必须写进文档的风险：无官方 API、Cookie 会过期、接口可能变更。

### 3.1 【17:20】坑 1：main.dart 不存在

**报错**：
```
Target file "lib\main.dart" not found.
```
**根因**：`rm` 删除旧 `main.dart` 后，重写时被工具拦下（"File has not been read yet"），实际**没有写入成功**，但后续步骤没有验证就继续跑了。

### 3.2 【17:21】坑 2：Gradle 与 Java 版本双双不达标

**报错（两层）**：
```
Your project's Gradle version (8.14.0) is lower than Flutter's minimum supported version of 9.3.1.
The Java version used for the build is 25.0.4, which is incompatible with Gradle 8.14.
```
**根因**：
1. 原工程 wrapper 是 Gradle 8.14（走腾讯镜像），Flutter 3.50 要求 ≥ 9.3.1。
2. Flutter 默认用了 Android Studio 自带的 **JDK 25**；Gradle 8.x 不支持 Java 25。
3. `gradle.properties` 里写的 `org.gradle.java.home` 被 Flutter 传入的 JVM 参数覆盖，**不生效**。

**当时的错误猜测**：以为加 `--android-skip-build-dependency-validation` 跳过版本校验就能用 AGP 8.11 编译。
**实测结论**：能过校验，但立刻暴露坑 3——**根本原因是 Flutter 插件与 AGP 8 的 API 不兼容，不是版本号检查的问题**。

**处理**：
1. 建 NTFS 目录联接绕开空格路径（SDK 与 JDK 都在 `D:\Program Files\` 下，Flutter 明确不支持带空格的 SDK 路径）：
   ```powershell
   New-Item -ItemType Junction -Path D:\AndroidSdk -Target "D:\Program Files\Android\android-sdk"
   New-Item -ItemType Junction -Path D:\Jdk17      -Target "D:\Program Files\Android\jdk-17"
   ```
2. `flutter config --android-sdk D:/AndroidSdk --jdk-dir D:/Jdk17`
3. `android/gradle.properties` 加 `org.gradle.java.home=D:\\Jdk17`
4. wrapper 升到 `gradle-9.5.0-all.zip`（腾讯镜像可用）

### 3.3 【17:22】坑 3：AGP 8 与 Flutter 插件 API 不匹配

**报错**：
```
'com.android.build.api.dsl.ApplicationDefaultConfig com.android.build.api.dsl.ApplicationExtension.getDefaultConfig()'
```
**根因**：Flutter 3.50 的 `flutter-gradle-plugin` 是按 **AGP 9.3.1** 的 API 编译的，`getDefaultConfig()` 在 AGP 8.11 上不存在。
**取证方式（关键方法）**：直接读 Flutter SDK 里的官方模板与常量，不猜：
```bash
grep templateDefaultGradleVersion  "/d/Program Files/Android/flutter/packages/flutter_tools/lib/src/android/gradle_utils.dart"
# → 9.5.0 / AGP 9.3.1 / Kotlin 2.4.20 / compileSdk 36 / minSdk 24
```
**处理**：`settings.gradle.kts` 升 AGP 9.3.1 + Kotlin 2.4.20。
**衍生**：AGP 9 换了 DSL，`app/build.gradle.kts` 必须重写（见 3.4）。

### 3.4 【17:24】坑 4：AGP 9 的 DSL 变更

**报错**：
```
Line 19: 'fun Project.android(configure: Action<BaseAppModuleExtension>)' is deprecated...
Line 29: 'fun BaseAppModuleExtension.kotlinOptions(...)' is deprecated. Please migrate to the compilerOptions DSL.
```
**根因**：AGP 9 默认 `android.newDsl=true`，旧的 `kotlinOptions { jvmTarget }` 被移除。
**处理**：重写 `app/build.gradle.kts`：
- `kotlinOptions` → 顶层 `kotlin { compilerOptions { jvmTarget.set(JvmTarget.JVM_17) } }`
- 加 `packaging { jniLibs { useLegacyPackaging = true } }`
- `minSdk` 显式写 **24**（Flutter 默认值也是 24；原工程用 `flutter.minSdkVersion` 会被 Flutter 的"自动升级脚本"反复改写）

### 3.5 【17:26 — 17:32】坑 5：NDK 缺失

**报错**：
```
Package ndk not found.
Package 28.2.13676358 not found.
Android sdkmanager did not install NDK 28.2.13676358 into D:/AndroidSdk.
```
**根因**：Flutter 插件会无条件为 app 模块设置 `ndkVersion = flutter.ndkVersion`（= 28.2.13676358），即使项目没有 native 代码。移除该行也无效。
**次要问题**：新 SDK CLI 的包名格式是 `ndk/28.2.13676358`（斜杠），不是旧的 `ndk;28.2.13676358`（分号）。用分号 grep 会误判为"仓库里没有这个版本"。
**处理**：
```bash
cd /d/AndroidSdk/cmdline-tools/latest/bin
yes | ./sdkmanager.bat --install "ndk/28.2.13676358"   # 2.1GB，约 3 分钟
```

## 7. 阶段五：用户首次验收反馈与修复（18:02 — 18:06）

用户在真机上试了第一版，报回三个问题。这一节记录**每个问题的根因分析**，因为其中两个的根因不止一处。

### 问题 1：退出播放页回首页后，点"继续收听"从头开始，没进度

**现象**：进播放页 → 返回首页（音频还在放）→ 点"继续收听" → 从第 1 秒重新开始。

**根因（三处叠加，只修一处不够）**：

| # | 根因 | 说明 |
|---|---|---|
| 1a | `TingPlayer.open()` 无条件重新加载 | 不管当前是不是正在放这一回，都走"下载 → open → 播放"。所以即使进度是对的，也会重新开始 |
| 1b | 进度落盘有 5 秒窗口 | `_saveProgress()` 由 5 秒定时器触发。用户听 3 秒就退出，Library 里还是 0；首页拿到 0 → 从头 |
| 1c | **seek 被 mpv 静默忽略** | `_mp.open()` 刚返回时文件头还没解析完，紧接着的 `_mp.seek()` 会被吞掉，位置停在 0。这是最隐蔽的一处，光把 `positionMs` 传对也不生效 |

**修复**：

- **1a** `open()` 增加同源判断：同一本书 + 同一回 + 状态属于 `playing/paused/preparing` → 直接复用（暂停则续播），**不重新加载**。
- **1b** `PlayerPage` 从 `StatelessWidget` 改为 `StatefulWidget`，`dispose()` 里 `unawaited(saveNow())`——离开播放页立即落盘。
- **1c** 新增 `_seekAfterReady()`：轮询等到 `_mp.state.duration > 0`（最多 4 秒）再 seek，seek 后 150ms 再校验一次位置，偏差超 5 秒则重 seek。
- **附带**：首页卡片改为**以播放器实时位置为准**（原来只看 Library 的陈旧值），文案变成"正在播放 12:30 / 已暂停 12:30 / 上次听到 12:30"，消除"明明在放却显示从头开始听"的误导。

### 问题 2：点书进播放页没反应，连点几次后过很久突然弹出一堆播放页

**现象**：搜索/书架点一本书 → 界面无变化 → 反复点 → 几十秒后一次弹出多个播放页。

**根因**：
```dart
// 旧代码（book_page.dart）
await TingPlayer.instance.open(_book, index, positionMs: resume);  // 这里要等下载完，几十秒
Navigator.push(...);                                              // 下载完成后才 push
```
- 首次播放要等整回下载完成，`await` 期间**界面毫无反馈**；
- 用户每点一次就挂一个新的 `await`；
- 下载完成后所有 await 同时恢复 → `push` 被连续执行 N 次 → 堆叠 N 个播放页。

**修复**：
- `_play()` 改为 **`unawaited(open(...))` + 立刻 push**：播放页自身有"正在准备这一回 45%"的进度圈，点击后立刻有反馈。
- 加 `_opening` 布尔锁挡住连点（在 `push` 返回后释放）。
- `open()` 内部的 `sameAsNow` 判断同时兜住了"同一回正在准备中又被点一次"的情况。
- 首页"继续收听"按钮同样改为不 await，避免同一问题。

**设计取舍**：用户原话是"应该在等待缓存结束才进入播放"。实际实现是"立刻进入播放页、准备好后自动出声"——因为等待期间没有任何反馈，才是导致连点的真正原因。行为上仍然是"缓存完成才开始播放"，只是把等待过程可视化了。

### 问题 3：夸克登录显示的是"下载夸克 App"页面，不是登录页

**根因**：WebView 默认 UA 是移动端。夸克判断为手机浏览器后，直接返回 App 下载引导页，根本不给登录入口。

**修复**（`QuarkLoginActivity.kt`）：

```kotlin
settings.userAgentString =
    "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 " +

```

- `textZoom = 115`：文字放大一点。

**遗留风险**：桌面版登录框默认可能是**扫码**。若用户手机就在手里、无法扫自己的屏幕，需要手动切到"验证码登录"标签。**此项必须真机复验**（见 [05-待办 T2](./05-待办与风险.md)）。

### 【18:12】发现版本号陷阱（重要）

**现象**：pubspec 写 `1.0.0+1`，但 APK 里 `versionCode` 是 **2001**。

**排查**：
```bash

```
**根因**：Flutter 的 `--split-per-abi` 会把每个 ABI 包的 versionCode 改写成 `ABI 序号 × 1000 + base`
（arm64=2xxx、v7a=1xxx、x86_64=4xxx），见 `FlutterPlugin.kt` 里的 `ABI_VERSION[abi] * 1000 + base`。

**影响（致命）**：如果按通用包填 `versionCode: 2` 发布，而手机装的是 arm64 包 2001，
自动更新会永远判定"已是最新"；反之则会被系统拒绝安装（降级）。

**决策**：**只发通用包**，versionCode 就等于 pubspec 的 build number，可预测。
`tools/publish.sh` 内置校验，用错产物直接报错退出。

### 【18:36 — 18:44】服务器部署

**先探环境**（不猜）：

```
Debian 12 / Docker 29.9.2 / 内存 1.6G（已用 514M）
nginx 已占 80、443；跑着 frps、rustdesk 两个容器
已有站点：ali.popcalico.top、nas.popcalico.top
证书：/etc/letsencrypt/live/wildcard-popcalico.top（覆盖 *.popcalico.top）
```

**关键决策：用子路径而不是子域名。**
原计划 `tingshu.popcalico.top`，实测 DNS 没有泛解析（`Non-existent domain`），
改 DNS 要等生效且有风险；而 `ali.popcalico.top` 已有 A 记录 + 泛域名证书覆盖。
→ 定 `https://ali.popcalico.top/tingshu/`：不动 DNS、不开安全组、证书现成。

**部署内容**：

```
/opt/tingshu/
├── docker-compose.yml   nginx:1.27-alpine，绑 127.0.0.1:8765，挂载 www/
├── nginx.conf           Accept-Ranges + version.json 禁缓存 + apk MIME
└── www/{version.json, tingshu.apk}
```

主机 nginx 在 ali 的 443 块里插入 `location /tingshu/ → proxy_pass 127.0.0.1:8765/`。

**踩的大坑（见 [04-P12](./04-故障排查手册.md)）**：
备份 nginx 配置时用了 `cp -a` 放在 `sites-enabled/`，
而那里的文件全是**符号链接**，`cp -a` 保留了链接属性，
加上 `include sites-enabled/*`（通配不看后缀）→ 同一份配置加载两次 →
`nginx: [emerg] a duplicate default server for 0.0.0.0:5660 test failed`。
**这次因为写了 `nginx -t` 失败自动回滚，没有影响线上 NAS 服务。**
修法：备份到 `/root/nginx-backup/`（用 `cp -L` 解引用），临时文件写 `/tmp`。

**端口连通的误判**：
本机 `curl https://ali.popcalico.top` 报 `SSL connection error / Connection was reset`，
一度以为 443 不通。用 `openssl s_client` 才发现**握手是成功的**：

```
Protocol version: TLSv1.3
Peer certificate: CN=*.popcalico.top
```

是 Windows curl 的 schannel 后端与 ECDSA 证书的兼容问题，不是服务器问题。
换 Python 请求立即 200。

**实测带宽**：

```
version.json  200  0.23s
8MB 分段下载  206  1.33s → 6.03 MB/s
```

6 MB/s 意味着 36MB 的包约 6 秒下完，**不需要上 OSS**（前一版文档建议上 OSS 是基于"ECS 带宽 1~5Mbps"的假设，
实测远超，该建议已作废）。

### 【19:20 — 19:26】问题 2：更新流程改成"一键 + 全自动"

**旧流程的每一步都是断点**：

```
启动 → 弹窗「有新版本」→ 点"现在更新"
     → push 一个整页 UpdatePage（第 1 次跳转）

     → 若缺安装权限 → 跳系统页 → 返回后要再点一次（第 3 次点击）
     → 下载完 → 系统安装页 → 点"安装"（系统强制）
```

老人独自在家时，任何一步被系统页面打断，就再也回不来。

**新设计**（`lib/widgets/update_prompt.dart`）：一个弹窗内的状态机，不再跳页面。

| 状态 | 界面 |
|---|---|
| idle | 大字版本号 + 说明 + **全宽 76dp 的「立即更新」** + 一行 15sp 的「以后再说」 |
| needPerm | 「最后一步」+ 说明"打开开关后返回，会自己开始更新"（已自动跳到系统页） |
| downloading | 进度条 + `34%　共 36 MB` + "下完会自动打开安装界面" |
| installing | "正在打开安装界面…" |
| done | "更新包已备好，去系统页面点安装" |
| failed | 错误原因 + 「再试一次」大按钮 |

**关键实现：从系统页返回后自动接上**，这是"不用点第二次"的核心：

```dart
@override
void didChangeAppLifecycleState(AppLifecycleState state) {
  if (state == AppLifecycleState.resumed && _phase == _Phase.needPerm) {
    _afterPerm();   // 重新查权限，有了就直接开始下载
  }
}
```

另外 `PopScope(canPop: 只有 idle 才允许)`：下载中按返回键弹窗不会消失，
避免老人误按后以为"更新没了"。

旧的 `update_page.dart` 整页删除，设置页的"检查更新"也走同一个弹窗。

### P1：WebDAV 客户端（`lib/services/nas/webdav_client.dart`）

**为什么选 WebDAV 而不是 SMB**：
1. 一份代码同时覆盖"家里局域网"和"外面经 frp 连域名"——SMB 跨网基本做不到
2. fnOS / 群晖 / 威联通 都原生支持，NAS 后台勾一下即可
3. 纯 HTTP，出问题 `curl` 就能验；Android 上的 SMB 库对协议版本太挑

实现要点：
- `PROPFIND Depth:1` 列目录、`walk()` 递归遍历（边遍历边 yield，可显示进度）
- XML 按 `localName` 匹配，**不依赖命名空间前缀**（各 NAS 的 `d:` / `D:` / 无前缀都不一样）
- `href` 归一化：可能是绝对 URL、可能是编码过的路径，还要去掉挂载前缀
- 下载支持 `Range` 续传（`.part` 语义），大文件给 10 分钟超时
- 错误统一翻成中文（"连不上 NAS（超时）。确认手机和 NAS 在同一个 WiFi"）

### P2：识别引擎（`lib/services/nas/scanner.dart`）

规则：**装着音频文件的那个目录 = 一本书**（作者目录因为没有直接音频，自然不算书）。

四层解析：
1. **作者**：内置 30 人评书演员表，路径任意一层命中即取，并从书名里删掉
2. **书名清洗**：剥分卷后缀（上部/第2部分/卷一）→ 剥容量标注（`（320回）`）→
   竖线分隔取书名号那段 → 剥噪音词（全本/完结/高清…）
3. **回目号**：`第N回` > `012-` > 纯数字 > 任意数字 > 文件顺序兜底，中文数字转阿拉伯
4. **分卷合并**：同名书自动并成一本书

## 14. 阶段七：双通道基线对齐（20:05 — 20:12）

### 【20:05】用户报的问题

> "现在手机里的旧版本，没法同步 beta 版的更新，你应该推送一版更新，
> 先让手机和其他设备的先更新到双分支版本啊"

**这是真问题，而且是我上一轮的逻辑漏洞。**

上一轮的做法是：1.1.6(code 10) 只推到 beta，标准线留在 9。
但"通道"这个功能本身是 code 10 才有的——**code ≤ 10 的客户端里 `version.json` 是写死的，
它们根本不知道 `version-beta.json` 存在**。

于是形成死锁：

```
旧手机（code 9）──只读──> version.json（code 9）
                              ↑ 相等，判定"已是最新"
                              ✗ 永远看不到 version-beta.json 里的 code 10
                              ✗ 因此永远学不会"切通道"
```

**教训**：给客户端加"更新机制本身"的新能力时，**这个能力必须先通过旧通道发出去**，
否则新能力只存在于一个旧客户端看不见的地方。

### 【20:06】给发布脚本加 `--both`

`tools/publish.sh` 原来只能 `--stable` 或 `--beta` 二选一。
新增 `--both`：同一个包同时写两份清单、上传两次。

```bash
./tools/publish.sh "说明" --both
```

实现要点（bash 数组式的循环，避免两段重复代码）：
- `TARGETS="stable beta"`，循环写清单、循环调 `deploy_server.py --${ch}`
- 两条线共用同一个 versionCode（这里是 11），**beta 设备切回 stable 不会被判降级**

文档 `06-自动更新与服务器配置.md` 新增 4.2 节，把"什么时候必须用 `--both`"写成规则表：

| 场景 | 做法 |
|---|---|
| 改了客户端要新增/变更更新机制 | **必须 `--both`** |
| beta 验证稳定要转正 | `--both`（同 code，不会降级） |
| 常规修 bug | 只推 beta |
| 确认发给老人 | 只 `--stable` |

## 16. 阶段九：书架末尾加推荐 + 设置页长文本挤压（21:00 — 21:08）

### 【21:00】用户要求

> "在我的书架的最后一个位置添加推荐的选项，顺便把截图的怪问题解决了"

截图里的怪问题：设置页「评书文件夹」整行被撑坏——
标题"评书文件夹"变成**每行一个字竖着排**，右侧值是
`(033)评书大全180G+10大名家+3714…`，还溢出到卡片外面。

### 根因：`BigRow` 的 value 没有宽度约束

```dart
Row(children: [
  Expanded(child: Text(title)),      // 有 flex，但没设 maxLines
  if (value != null) Text(value!),   // ← 非 flex，Row 给它的宽度是"想要多少给多少"
  ...
])
```

`Row` 里非 flex 的孩子按**固有宽度**排布，超长文本会把整行宽度吃掉，
`Expanded` 的标题只剩几个像素宽 → 中文按字换行 → 竖排；
同时整行超出容器宽度 → `RenderFlex overflowed by 229 pixels`。

### 修法（`lib/widgets/common.dart`）

1. `LayoutBuilder` 取实际可用宽度，value 最多占 **45%**（`ConstrainedBox`），
   `maxLines: 1` + `ellipsis` + 右对齐；
2. 标题 `maxLines: 2` + `ellipsis`，永远不会被压成竖排；
3. 设置页的文件夹名再额外截断：
   `(033)评书大全180G+10大名家+3714集` → `(033)评书大…714集`
   （保留头尾，完整名字在选文件夹的弹窗里能看到）。

### 【21:02】书架末尾的推荐入口

## 17. 阶段十：媒体控件闪退 + 边播边存（11-21 20:30 — 21:40）

用户反馈两件事，都是"能不能正常用"级别：

### 17.1 闪退：折叠通知的按钮索引越界

#### 现象

一台手机通知栏/锁屏没有播放控件，另一台**一播放就闪退**。同一份代码，两台机器两种表现。

#### 根因

`lib/player/ting_player.dart` 的 `_pushState()` 里：

```dart
controls: [
  if (hasPrev) MediaControl.skipToPrevious,   // 第一回没有
  MediaControl.rewind,
  if (isPlaying) MediaControl.pause else MediaControl.play,
  MediaControl.fastForward,
  if (hasNext) MediaControl.skipToNext,       // 最后一回没有
],
androidCompactActionIndices: const [0, 2, 4],   // ← 写死
```

`controls` 是**动态长度**：中间回 5 个，第一回/最后一回只有 4 个，单回书只有 3 个。
而 `[0, 2, 4]` 里的 `4` 在 4 个元素时已经越界。

audio_service 只在 **Android 12 及以下**（`SDK_INT < 33`）才调用
`MediaStyle.setShowActionsInCompactView(compactActionIndices)`；
`NotificationCompat.MediaStyle.applyTo()` 会按索引去 `mActions.get(i)`，
越界直接抛 `IndexOutOfBoundsException`。

- **Android ≤12**：构建通知时抛异常 → Service 主线程崩溃 → **整个 App 闪退**
- **Android 13+**：不走这段代码，不崩，但通知/锁屏表现异常（用户说的"无效"）

Dart 侧只有 `assert(length <= 3)`，**不校验索引是否在范围内**；
release 包 assert 被移除，越界值会原样传给原生。

#### 修法

1. 索引从 `controls` 现算，并过滤掉不存在的键：

```dart
final compact = compactActionIndices(controls, playPause);
```

2. 抽成顶层纯函数 `compactActionIndices()`，并新增 `test/media_controls_test.dart`：
   穷举 `hasPrev × hasNext × playing` 共 8 种组合，断言每个索引都 `< controls.length`，
   且折叠视图中间那个键一定是播放/暂停。

#### 顺带修掉的三个隐患

| 问题 | 后果 | 修法 |
|---|---|---|
| `_pushState()` 被进度流每 100~200ms 调一次，每次重发 `MediaItem` + `PlaybackState` | 每秒重建通知十几次：闪、按钮点不动、低端机 ANR | 800ms 节流；`MediaItem` 只在回目/时长变化时发；播放/暂停等用 `force: true` 立即发 |
| 通知封面用 B 站原图，无 Referer | 图床 403，通知栏一块空白 | `artHeaders: Referer`；`artDownscaleWidth/Height = 400` 防大图 OOM |
| `stop()` 把 `_item` 清空 | 通知被滑走/误触"停止"后，首页"继续收听"跟着消失 | 只停声音，保留当前书和进度 |

#### 关于"我的手机无效"的排查结论

代码里原本就有首页顶部的"通知没打开"提示条，但**从旧版本升级上来的手机
`setupDone` 早就是 true，再也不会走首次配置向导，也就从来没申请过
Android 13 的通知权限**——这一类设备的表现就是"通知栏什么都没有"。

在设置页新增了**「媒体控件自检」**（`NotifyPermission.diagnose()`），
一次列出：机型/Android 版本、通知权限、通知总开关、"评书播放"这个通知类别是否被关掉，
并给出对应的一句话结论。查不出来的才归到 ROM 身上。

### 17.2 一直转圈：改成"边听边存"

#### 现象

长回目（一集四五十分钟、几十上百 MB）点开要转圈几十秒，
老人以为坏了就退出。旧逻辑是 `CacheEngine.obtain()` **整回下载完**才
`_mp.open(本地文件)`。

#### 修法

`_playCurrent()` 分两条路：

```dart
final cachedPath = _cache.cachedPath(...);
if (cachedPath != null) {
  await _mp.open(Media(cachedPath));            // 存过：本地秒开
} else {
  final audio = await _resolve(b, ch);          // 只解析直链（1 次 API）
  await _mp.open(Media(audio.url,
      httpHeaders: audio.headers));             // 立刻开播
  unawaited(_cache.saveInBackground(...));      // 后台补齐本地缓存
}
```

关键点：

1. **先出声，再存盘**。解析直链只要一次接口调用，不再等整回下载。
2. **后台补存走的是同一条 `_downloadFrom`**，完成后正常进索引，
   下次这一回就是本地秒开、断网也能听。
3. **看门狗兜底**：8 秒还读不出时长，说明这条直链流不动（CDN 不支持分段 /
   链接过期），自动退回"下载完再播"，`await` 的是后台那个下载任务，**不会重复耗流量**。
4. `cachedPath()` 原来只查内存索引，现在**同时检查文件是否存在**：
   缓存目录被系统清理、被用户清空之后，索引还在但文件没了，
   旧写法会把一个不存在的路径交给播放器，表现为"点开就报错"。

#### 验证（真机网络，模拟器 API 37）

清空缓存后点"继续收听"（第 2 回，33.2MB，从 9:42 续播）：

|---|---|---|

## 18. 阶段十一：清除全部数据（模拟新机）（11-21 22:40 — 23:25）

需求一句话：

> 添加一个清除全部数据的功能，模拟新机

### 18.1 功能定位

这是**家属专用**的操作：换人用、彻底重来、儿子把手机还给老人之前。
放在设置页最底部（老人不会翻到这里），红色文字，**两道确认**：

1. 第一道讲清楚删什么、不删什么——"书本身还在网盘和 B 站上，不会丢"
2. 第二道强调"没法撤销"，按钮是红色的"确认清除"

确认后是全屏遮罩"正在清除…"，不可取消、拦掉返回键，防止清到一半被打断。

### 18.2 清哪些东西

| 位置 | 内容 |
|---|---|
| `shared_prefs` | 书架、听到哪儿、夸克登录、更新设置、首次配置标记 |
| `databases` | 目前没用到，防御性清理 |
| 内部 `files` / `cache` | 应用私有文件 |
| 外部私有目录 | 音频缓存 `ting_audio`、下载的安装包 `update` |

**不清**系统授权（通知、后台、安装未知应用）——应用内改不了，
在确认框里明确写了，免得用户以为能"重置权限"。

### 18.3 踩的两个坑（都跟"重启"有关）

#### 坑一：杀进程 + AlarmManager 拉起 → 停在桌面

第一版是清完 `killProcess()`，再用 `AlarmManager.set` 预约 300ms 后拉起启动页
（ProcessPhoenix 的经典做法）。实测：进程确实死了，但**应用没有重新起来**，
停在桌面。原因是 Android 10+ 对后台启动 Activity 的限制把 PendingIntent 拦掉了。

用户视角这就是"点了个按钮闪退"。

#### 坑二：`recreate()` → 也停在桌面

第二版改 `Activity.recreate()`。结果同样停在桌面——
FlutterActivity 重建时拿不到新引擎（我们没配 cached engine），
新旧引擎交替把 Activity 弄没了。

#### 最终方案：清磁盘 + Dart 侧重置内存 + 直接跳向导

不再纠结"重启"，分成两半：

- **原生只删磁盘文件**，不做任何生命周期操作；
- **Dart 侧**把内存状态归零，然后 `pushAndRemoveUntil(SetupPage)`。

### 18.4 最隐蔽的坑：清完数据会"复活"

第一版清完磁盘后，冷启动一看——书架回来了、向导又显示"已配置"。

根因：**Android 的 SharedPreferences 每次写入都会把内存里的整份 map 序列化回磁盘**。
Dart 侧的 `SharedPreferences` 是单例，内存里还留着旧 map；清除后只要发生**任何一次写入**
（比如 Activity 暂停时 `saveNow()` 保存播放进度），旧数据就整份写回去了。

修法两条一起上：

1. `AppWipe.wiping = true`：清除期间 `Library._save()` 直接 return，挡住所有写入；
2. 清完后 `(await SharedPreferences.getInstance()).clear()`：把插件内存 map 也清空，
   再调各服务的 `resetForWipe()` 把字段归零，最后才放开 `wiping`。

漏掉哪一条都会出现"清完又长回来"。

| 项 | 结果 |
|---|---|
| 两道确认 | ✅ 文案、按钮、红色强调都正常 |
| 清除后界面 | ✅ 直接回到"先设置 3 项"的首次配置向导 |
| 进程 | ✅ pid 前后一致（5255），不是靠杀进程实现的 |
| 缓存目录 | ✅ `files/` 已空，`ting_audio/` 只剩空目录 |
| 冷启动 | ✅ force-stop 后重启仍是向导，**数据没有复活** |
| 播放中清除 | ✅ 先 `stop()` 再清，不会因为缓存文件被删而报错 |

## 19. 阶段十二：媒体控件仍然不好使（11-21 23:27 — 23:50）

用户反馈：**"媒体控件依旧不好使"**，让联网查。

### 19.1 查到了什么

三条关键资料：

1. **Android 13 起媒体控件不再用我们的通知按钮**
   （[官方行为变更](https://developer.android.com/about/versions/13/behavior-changes-13)）
   系统按 `PlaybackState` 自己渲染最多 5 个槽：播放/暂停、上一首、下一首、两个自定义。
   也就是说 `MediaStyle` 里的 action 列表在 13+ 上**完全不参与渲染**，
   我们之前修的 `setShowActionsInCompactView` 只对 Android 12 及以下有效。

2. **audio_service 0.18.19 把通知渠道固定写成 `IMPORTANCE_LOW`**
   ```java
   channel = new NotificationChannel(id, name, NotificationManager.IMPORTANCE_LOW);
   ```
   而且从不设置 `CATEGORY_TRANSPORT`。
   LOW 渠道在小米/华为/OPPO 上会被当成"次要通知"：**锁屏不显示、通知栏不给按钮**。
   多个开源项目（BiliSail、PureLive、songloft）都在为这个插件打补丁。

3. **国产 ROM 的额外拦截**：锁屏视为"非交互区"丢弃媒体按钮广播、
   未获得"锁屏通知显示"权限时 NMS 强制降级渠道、后台服务管控。

### 19.2 这一版做了什么

**核心修法：抢在插件之前把渠道建好，用 `IMPORTANCE_DEFAULT`。**

```kotlin
override fun onCreate(...) {
    ensureAudioChannel()   // 必须在 AudioService.init 之前
}
```

插件建渠道前会先查同名渠道，有就跳过——所以谁先建谁说了算。

**踩坑：换渠道 ID 而不是删了重建。**
第一次尝试是"发现已有渠道重要性 < DEFAULT 就删掉重建"，
结果 `dumpsys` 显示还是 `mImportance=2`。原因是 Android 会记住
"这个 ID 被删过"，重建请求直接被忽略。最后换成新 ID `cn.tingshu.audio.v2`，
旧渠道 `cn.tingshu.audio` 顺手删掉。重装后确认 `mImportance=3`。

**新增"发测试通知"**（自检弹窗里）：
用同一个渠道发一条普通通知。用户点一下就知道——
- 能看到 → 通知权限/渠道都正常，问题在媒体会话侧；
- 看不到 → 通知根本没被系统放出来，先解决权限或 ROM 拦截。

这是把"媒体控件不好使"一刀切开的最快办法，比反复猜管用。

**自检里补上渠道重要性等级**：
"默认 / 高 / 低（锁屏可能不显示）/ 最低 / 已关闭"，
并给对应结论。之前只显示"正常/不正常"，看不出差在哪一级。

### 19.3 验证

| 项 | 结果 |
|---|---|
| 新渠道重要性 | ✅ `mImportance=3`（DEFAULT），旧渠道 2 已废弃 |
| 自检显示 | ✅ "评书播放"类别 → **默认** |
| 测试通知 | ✅ 通知栏正常显示"通知能看见" |
| 媒体控件（1.1.10 已验证） | ✅ 封面 + 书名 + 五键 + 暂停/播放有效 |

### 19.4 还需要用户确认的

真机是"完全没有媒体卡片"还是"有卡片但按钮不对"，决定了下一步方向：

- 完全没卡片 → 锁屏通知权限 / ROM 媒体卡片开关
- 有卡片但少按钮 → Android 13+ 只给 5 个槽，快进快退要靠自定义槽
- 有按钮但点了没反应 → 媒体会话回调断了（`MediaButtonReceiver` 被 ROM 拦）

## 20. 阶段十三：网盘扫描按"书/卷"两级识别 + 分组加入 + 调试项收进测试版（11-21 23:50 — 00:35）

### 20.1 用户反馈

> "现在确实可以解析网盘中的多个目录夹文件结构，但是解析完之后，就把所有的音频文件
> 一股脑的展示出来，不能正确分组按组加入书架，另外把调试用的设置选项在选标准时隐藏，
> 在beta时才显示，如清数据、测试通知等"

### 20.2 根因：只认"装音频的目录 = 一本书"

旧规则（`NasScanner.scan`）是"音频文件所在的那一层目录就是一本书"。
它只解决了"作者 / 书名 / 上部-下部"这一种嵌套，**没有处理再往下的一层**：

```
评书/单田芳/水浒传/001/001.mp3          ← 每集一个文件夹
评书/单田芳/水浒传/001-050/001.mp3      ← 按回数区间分文件夹
评书/单田芳/水浒传/CD1/01.mp3           ← 按碟号分文件夹
```

每种摆法都会把**一层目录**当成一部书：一部 320 回的水浒传变成 100 多本"书"，
每本名字是 `001`、`002`…… 添加页看到的就是"所有音频文件堆在一起"。

### 20.3 改法：先建树，再两级判定

`scan()` 不再按父目录字符串分组，改成先建出目录树（`_DirNode`），再递归判书：

1. **本目录直接摆着音频** → 它就是一本书；
   同目录下如果是「上部 / CD1 / 001-050 / 第12回」这种**卷目录**，并进这本书。
2. **本目录没有音频，但含音频的子目录全是卷目录** → 整个子树是一本书
   （书目录比音频高一层的情况，比如根部选的就是《水浒传》文件夹）。
3. 其余子目录各自递归成书。

"卷目录"的判定（`_isPartDir`）：
- 清洗后什么都不剩的名字（上部 / 下册 / 卷一）一定算卷；
- 纯数字（`001`）、数字区间（`001-050`）、碟号（`CD1` / `disc 2` / `part03`）、
  集号（`第12回…`）**只有父目录像书名时**才算卷——否则
  `武侠/01/`、`武侠/02/` 这种"数字目录本身是一本书"的摆法会被并成一本《武侠》。

顺带修两个显示问题：

- **书名带编号**：`01 水浒传` → `水浒传`（`_cleanTitle` 剥掉前缀编号）。
  不剥的话分组头和书架卡片上都是"01 水浒传"。
- **每段重新编号**：CD1 的 001-002 + CD2 的 001-002，全局回目号重复，
  原来按回目号排序会把两张碟穿插成 1、1、2、2。
  现在 `NasChapterDraft` 多带一个 `part`（第几段），**只在回目号重复时**先按段排。

### 20.4 添加页：分组 + 整组加入

新增 `lib/services/book_group.dart`：

- 组名 = 书路径的第一段（`/单田芳/水浒传` → `单田芳`）；
- 第一段就是书名时（`水浒传/上部`）不当组名，退到作者名，再退到「未分组」；
- 「未分组」永远排最后。

`add_page` 从"平铺书列表"改成：

- 顶部一句汇总："共 N 部书、M 个音频，按文件夹分成 X 组"；
- 每组一个头：组名 + `N 部 · M 回` + **整组加入**（点组名可折叠）；
- 每本显示 `作者 · N 回`，已在书架的显示绿色对勾；
- 整组加入**不跳播放页**（家属一次加十几本，每本都跳走会烦），
  加完留在原地报"已把「单田芳」12 部加入书架"；
- 只剩一组时不套分组头，直接列书。

### 20.5 调试项只在测试版显示

设置页新增 `final beta = UpdateService.instance.channel == UpdateChannel.beta;`：

- **标准版**：看不到「媒体控件自检」「重新做一遍初始设置」「清除全部数据」；
- **测试版**：多一节「调试（只在测试版显示）」，三项都在。

理由：这几项对老人是纯风险——"清除全部数据"点错就是灾难，
"重新做初始设置"会把已经配好的向导推翻重来。

## 21. 阶段十四：更新后"变新机"（数据丢失）+ 书架备份（11-22 00:00 — 01:05）

### 21.1 用户反馈

> "手机更新完版本之后，没有存储，之前的配置，变成全新安装了一样了，
> 另外我的手机(卓易通)依旧没有媒体"

### 21.2 根因：启动时的"没读完就当没有"

应用自己的更新流程（系统安装器 + 同包名同签名）**不会**删数据，
全工程也只有设置页「清除全部数据」会删。真正的坑在启动顺序：

```dart
await Future.wait([Library.load(), QuarkApi.load(), CacheEngine.load(), UpdateService.load()])
    .timeout(const Duration(seconds: 8));
```

升级后第一次启动要 dexopt，很容易超过 8 秒。超时被 `catch` 吞掉后：

1. `Library._ready` 还是 false、书架还是空；
2. 启动页按 `setupDone` 判定"没配置过" → 弹**首次配置向导**；
3. 用户按"跳过"→ `markSetupDone()` → 首页；
4. 播放/加书触发 `_save()`，把**内存里的空书架**整份写回磁盘。

到第 4 步，真数据就被覆盖了。用户看到的就是"更新完变成全新安装"。
`Library.load()` 还有一个隐患：整段只有一个 try，任何一项类型不对就中途抛异常，
表现出完全一样的症状。

### 21.3 改法（三处，缺一不可）

1. **`Library.load()` 不再抛异常**：逐项读、逐项兜底（`_readString/_readInt/_readBool/_readStringList`）；
   书架 JSON 坏了就把原文另存 `ts_shelf_broken` 再继续，不卡住其它字段。
2. **`_save()` 加 `_ready` 守卫**：本地数据没读完，一律不写盘——
   绝不让空书架覆盖真数据。
3. **启动顺序**：`Library.load()` 单独 await（10 秒 + 重试一次），
   不再和其它服务挤在一个总超时里。

### 21.4 备份：书架 + 设置存一份到公共目录

新增 `lib/services/backup_service.dart` + 原生 `tingshu/backup` 通道：

- **主备份**：`/sdcard/Android/media/<包名>/听评书/听评书-备份.json`（应用可直读直写、无需权限）
- **副备份**：`下载/听评书/听评书-备份.json`（家属能在文件管理器里看到，方便迁到新手机）
- 内容：书架（含每本听到第几回、第几秒）、听过清单、首次配置标记、播放源、
  夸克选的目录、更新通道。**不含夸克 Cookie**（账号凭证不能落公共目录）。
- 触发：书架/设置变化时（限频 2 分钟）、退到后台时、启动时各写一次；
  **书架为空而备份里有书时拒绝覆盖**（这是救回数据的唯一一份）。
- 恢复：启动时若磁盘上"本来什么都没有"（`hadStoredState == false`）自动恢复；
  首页发现"书架空 + 备份里有书"会问一句"要恢复吗"（点"不用了"会记住，不再骚扰）；
  首次配置页顶部也会出现"找到一份备份，里面有 N 部书 · 恢复"。
- 清除全部数据时连备份一起删，否则清完一启动又被恢复回来。

**验证过程中踩到的两个坑**：
- `pm clear` 会连 `Android/media/<包名>` 一起删，也会删掉 MediaStore 记录；
  文件虽在 `Download/`，但 scoped storage 下按路径读是 EACCES。
  所以备份只能防"数据被覆盖/读坏"，防不了"整包重装"——后者需要换机时手动拷文件。
- 启动时的补备份会把刚注入的"有书备份"覆盖成空书架。加了"不覆盖更丰富的备份"规则才拦住。

### 21.5 卓易通为什么没有媒体控件

查到的公开信息一致：卓易通是鸿蒙 NEXT 上跑安卓应用的兼容层，
安卓的 `MediaSession` **不会**被桥接到鸿蒙控制中心
（网易云音乐官方客服也说明过"控制中心不展示正在播放的歌曲"）。
这不是本应用的 bug：同一版 APK 在普通安卓上（模拟器实测）通知栏五键、锁屏、
暂停/下一回都正常。应用内自检弹窗已加一句说明，避免继续误判。

## 22. 阶段十五：夸克能解析、不能播（11-22 00:28 — 01:00）

### 22.1 现象与判断

用户："夸克网盘内容可以解析，但无法播放。"

能解析说明 **Cookie 有效**（列表接口和取直链接口用的是同一套登录态），
所以问题落在"直链能不能真的取到内容 / 播放器能不能读"这两步。

### 22.2 这一版做的三件事

1. **流播报错立刻转下载**（`_watchStreamFallback` 增加错误基线）：
   以前只有"8 秒读不出时长"才退回下载；现在 mpv 一报错（403 / 链接过期 /
   格式不支持）马上转"下载完再播"，不用干等。
   基线必须在 `_open` **之前**取——mpv 有时在 open 过程中就报错。
2. **错误提示细化**（`_friendly`）：401/403 → 地址被网盘拒、建议重新登录；
   404 → 文件找不到了；QuarkException 直接透出网盘原话。
3. **播放诊断**（设置 → 调试 → 播放诊断，仅测试版）：
   按顺序报告——书/回目/文件标识/大小 → 是否登录 → 取直链耗时 →
   直链域名与参数 → 真实发一次 `Range: bytes=0-2047` 请求，
   输出 HTTP 状态、内容类型、长度、是否支持分段、实际读到多少字节，
   并给出一句结论。可一键复制发给家属。

   写这个功能时踩了一个自己挖的坑：等待框用了 `await showDialog(...)`，
   导致后面诊断代码永远执行不到（界面卡在"正在检查…"）。
   改成 `unawaited(showDialog(...))` 再手动 pop。

### 22.4 真凶（用户跑诊断后一次定位）

用户发回的诊断截图：

```
取直链：失败 —— type 'List<dynamic>' is not a subtype of type
'Map<dynamic, dynamic>?' in type cast
```

`QuarkApi._request` 把信封里的 `data` 一律按对象强转：

```dart
return (data['data'] as Map?)?.cast<String, dynamic>() ?? {};
```

但 `/file/download` 返回的 `data` **是数组**（`[{fid, download_url}]`）。
于是"列目录"（`/file/sort`，data 是对象）一切正常，
**唯独取直链必抛类型异常** → 所有夸克内容都能解析、全都播不了。

修法：
- 新增 `_requestRaw`：只解信封、返回 `data` 原样；
  `_request` 在它上面套一层"是对象才返回对象"，供列表/详情用。
- `downloadUrl` 走 `_requestRaw`，并抽成纯函数 `extractDownloadUrl`，
  同时认 `data` 为数组 / `{list: [...]}`、字段 `download_url` / `url`。
- 新增 `test/quark_download_test.dart`（6 例）锁住这几种形状。
- 播放诊断的结论也加了这一分支：看到 type/cast 就直说"老版本 bug，升级即可"。

**教训**：同一个 API 客户端里，"信封解包"和"业务字段解析"必须分开。
把 `data` 硬编码成 Map，只是**恰好**对列表接口成立，换个接口就炸，
而且错误信息（type cast）离业务十万八千里，用户只会说"播不了"。

## 24. 阶段十七：NAS 扫描"没有音频文件"的三个真因（11-22 12:30 — 12:52）

### 24.1 现象

用户配好 frp 隧道后："nas文件也是复合的提示没有音频文件"。
实际目录很简单：

```
/book/袁阔成/袁阔成_三国演义/三国演义1.mp3
/book/袁阔成/袁阔成_三气周瑜/…mp3
```

一共 14 部书、848 个音频，结构完全标准，理应一扫就出。

### 24.2 定位手法：用 App 同一套代码直连真机 NAS

新增 `tools/nas_probe.dart`：直接 `import package:tingshu/services/nas/webdav_client.dart`，
用**和 App 完全相同的代码**请求真实 NAS，打印每一层的返回。
比在模拟器里点界面快得多，而且能看到调用栈。

第一轮就跑出两个错误：

```
--- list("/book") ---
list FAIL: Invalid argument(s): Illegal percent encoding in URI
#2  WebDavClient._parseMultiStatus (webdav_client.dart:251)
```

### 24.3 三个 bug（缺一不可，任何一个都会导致"扫不出音频"）

**① 列目录没带结尾斜杠 → 被 301 → 拿到空响应**

`_uri('/book')` 生成 `.../dav/book`。fnOS 对"目录没有斜杠"会 301 到 `/book/`，
而 **PROPFIND 这类自定义方法，HttpClient 不会自动跟随重定向**。
于是拿到 301 的空 body，`if (body.isEmpty) return []`，
`walk()` 把它当"这个目录是空的"直接跳过——一个音频都拿不到。

修：`_uri` 保留结尾斜杠；`_listRaw` 请求目录时强制补 `/`。
另外把状态码卡死：只认 207/200，其它一律抛错，**绝不静默当空目录**。

**② 文件名被二次解码 → 抛异常 → 整层目录作废**

`_hrefToPath()` 里已经 `Uri.decodeFull()` 解过一遍（`%E8%A2%81…` → `袁阔成`），
`_parseMultiStatus` 又对 name 做 `Uri.decodeComponent()`。
Dart 的 `decodeComponent` 是严格的 UTF-8 百分号解码，对已解码的中文/含 `%` 的名字
会抛 `Illegal percent encoding in URI`，整个响应解析失败。

修：name 不再二次解码；保留 `_safeDecode` 只兜"上层没解码"的情况，且失败时原样返回。

**③ 纯演员名目录被当成"卷目录" → 14 本书并成 1 本**

这个最隐蔽，是**修完 ①② 之后才暴露的**：

```
=== scanCheck root=/book 文件数=838 ===
识别出 1 本书
  《book》 作者=  834 回
```

`_isPartDir` 里"清洗后为空 → 一定是卷名（上部/卷一）"这条规则，
把 `袁阔成/` 也判成了卷——因为 `_cleanTitle` 会把已知演员名整个剥掉，结果为空。
于是父节点 `袁阔成` 的所有子目录都被视为"卷"，整棵子树合并成一本《book》。

修：清洗后为空时，先排除 `knownActors` 里的纯演员名——**作者目录不是卷**。

修完立刻正确：

```
识别出 14 本书
  《三国演义》 作者=袁阔成  365 回
  《封神演义》 作者=袁阔成  200 回
  《彭公案》   作者=袁阔成   86 回
  …（共 14 本、848 个音频）
```

### 24.4 播放链路验证

```
HTTP=206  type=audio/mpeg  got=2048  time=0.31s
content-length: 3450516   accept-ranges: bytes
```
支持 Range，边听边存可用。

### 24.6 教训

1. **"空结果"必须能区分"真没有"和"请求失败"**。`catch (_) { continue; }` 和
   `if (body.isEmpty) return []` 是这次排查耗时最长的原因——错误被两层静默吞掉。
2. **WebDAV 的目录一定要带尾斜杠**，且自定义 method 不跟随重定向，两个坑叠在一起。
3. **兜底规则之间会打架**：\"清洗后为空 = 卷名\" 在夸克那套结构里是对的，
